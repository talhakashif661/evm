## 2. Functionality status — what's verified vs. what isn't

The backend exposes **62 API route handlers** across 11 controllers
(`admin, ai, auth, bid, booking, complaint, ev, review, slot, station,
verification`). Here's the honest breakdown of what's actually *proven* to
work vs. merely *present*:

### ✅ Verified working (backed by a live-passing test)
The e2e suite exercises the full critical path end to end:
- Admin bootstrap, registration + login for **every** role, role guards
- Station lifecycle (owner creates → admin approves)
- Time-window bookings **with overlap/race-condition rejection**
- Check-in cost-locking, Stripe webhook idempotency (pays exactly once),
  completion
- Full auction flow (bidding, priority scoring, closing, auto-booking)
- Admin dashboard + audit trail, complaints inbox, verified-purchase reviews
- Logout revoking the token server-side

### ⚠️ Present but NOT directly tested (works in code-trace, no assertion)
These aren't *broken* — they're just not covered by an automated test, so
"working" rests on code inspection, not a green checkmark:
- **AI recommendation endpoint** (`ai.controller`) — no test touches it
- **Email OTP happy path** (`verification.controller`) — validation errors
  are tested, but a real successful OTP verification isn't (flagged back in
  Phase 7.1 too)
- **Live Socket.IO delivery** — the auction *logic* is tested, but actual
  real-time socket push to a connected client isn't (needs a live server)
- **EV CRUD and slot management** — used as test *setup*, but their own
  endpoints aren't independently asserted

### 🚫 Cannot be verified in this environment at all (no live browser)
- Whether pages render without **browser-console errors**
- Real click-through **404 testing** across navigation
- **Mobile responsiveness** at real viewport widths (only ever code-audited)
- Whether the hero/design **looks right** visually

## 4. Environment / deployment caveats

1. **⚠️ Backend won't fully boot in a no-internet sandbox.** Prisma's query
   engine binary downloads during `npm install` (`prisma generate`), and
   that download is blocked in this sandbox. On your machine or any normal
   deploy box it works fine. The code now fails *gracefully* here — `npm run
   doctor` and the startup path both explain the cause instead of dumping a
   raw stack trace — but **you should confirm the backend boots on a real
   machine before calling deployment verified.** This is the single most
   important item to check.
2. **Frontend `esbuild`/`vite` vulnerability** (1 moderate, 1 high, dev-only)
   — pre-existing since Phase 6. The fix requires a **major Vite version
   bump** (breaking change), deliberately left out of scope. It affects the
   dev server only, not production output.
3. **No real database in this sandbox** — all tests use an in-memory mock,
   so nothing here has run against actual MongoDB. `npm run doctor` will
   verify a real connection once you point `DATABASE_URL` at one.
